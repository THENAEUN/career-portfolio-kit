# 작성 전 JD 기준과 인수조건

## 기준을 만드는 순서

1. JD 원문을 날짜·출처와 함께 개인 QA 폴더에 보존하고 SHA-256을 계산한다. 회사·직무·지원 언어·제출 분량/형식을 확정한다. 문구를 고치거나 웹페이지를 다시 읽었다면 어느 스냅샷을 기준으로 했는지 남긴다.
2. **명시 필수요건 / 주요업무 / 우대사항**을 분리한다. 공고의 인용 위치를 항목마다 붙인다. 직무로부터 추론한 역량은 `inferred`로 표시하고 회사가 명시한 요구조건처럼 설명하지 않는다.
3. 요건을 관찰 가능한 인수조건으로 바꾼다. 예: `C++` → `본인 담당 기능, C++을 사용한 구현 범위, 동작·시험 결과를 설명`. 핵심어 출현만으로 충족으로 보지 않는다.
4. 정본 자료를 대조해 `직접 근거 / 인접 경험 / 본인 진술 / 없음·추가 확인`을 구분한다. 경력 연수·학위·필수 자격 같은 명시적 지원 조건은 수사로 대체할 수 없는 별도 조건이다. 학생 공고에 시니어 수준 실차 양산 경험을 임의로 추가하지 않는다.
5. 이력서에는 간결한 행동·역할·결과를, 포트폴리오에는 구조·선택·검증·시각 근거를 배치한다. 각 항목의 문서별 인수조건을 고정한 뒤 작성한다.

JD가 없으면 목표 직무 기반 **임시 구성 계획**만 만든다. JD를 받기 전에는 JD 적합 점수·필수요건 통과를 산출하지 않는다. 사용자에게 자체 기준의 요약과 실제 부족 근거를 알리되 모든 작성 작업에 새 승인을 요구하지 않는다.

## 배점 기본값

| category | 내용 | 기본 배점 |
|---|---|---:|
| must_have | JD 필수 역량·요건의 문서상 증거 | 35 |
| responsibilities | 주요업무 수행 가능성을 보여주는 경험 | 25 |
| preferred | 우대사항 관련 근거 | 10 |
| ownership_outcomes | 개인 기여·판단·구체적인 결과/산출물 | 15 |
| communication | 직무 중심 구성·읽기·문장·시각 설명 | 10 |
| completeness | 필요한 정보·관련 링크·제출 구성 | 5 |

배점을 해당 category의 항목에 나눠 전체 합계를 100으로 맞춘다. 우대사항이 없는 JD라면 가짜 항목을 만들지 않고 나머지 배점을 비례 재배분한다. 직무에 맞춰 가중치를 바꿀 수 있지만 작성 전에 이유를 기록하고 고정한다. `must_have`, `responsibilities`에는 각각 적어도 한 항목이 필요하다. 명시적 필수가 없는 공고는 임의의 학위·연수 조건 대신 직무상 필요한 역량의 추론임을 표시한다. 예시 값은 기업의 실제 합격선이 아니다.

명시된 **지원 필수 자격**은 `critical: true`로 표시하며 `category: must_have`, `source_type: explicit`이어야 한다. 학위·경력 연수·필수 자격증·근무 자격 등의 충족 여부는 근거표에서 따로 `pass / fail / unknown`으로 판정한다. 단지 경험이 더 풍부하면 좋은 우대사항을 critical로 지정하지 않는다.

포트폴리오의 communication 항목에는 [디자인 인수조건](../../html-pdf-portfolio/references/design-review.md)과 [회사·프로젝트 챕터 구성](../../html-pdf-portfolio/references/chapter-structure.md)을 반영해 Summary와 상세 성과의 연결, 회사·역할·기간 경계, 핵심 결론·근거 가독성·정보량·일관성·사용자 팔레트 반영을 평가한다. 이력서는 A4 본문 위계와 스캔 가능성을 평가한다. 별도 취향 점수를 추가해 합계 100을 넘기거나, 리뷰 후 배점을 바꾸지 않는다.

프로젝트별 대표 한 페이지에는 [성과 중심 명사형 제목·문제/해결/성과·가변 이미지 배치 기준](../../html-pdf-portfolio/references/project-onepager.md)을 적용한다. 제목·Summary에서 검증된 성과와 개인 기여가 먼저 보이는지, 회사→프로젝트 계층·결과 조건·원본 이미지 비율과 실제 PDF 가독성을 확인한다. 미측정 작업에 숫자 성과를 강요하거나 좌측 배치만 통과시키거나 장식적 레이아웃 변화 자체를 가점하지 않는다.

## 기준 JSON 계약

`criteria.json`은 다음 구조를 따른다. 아래 한 항목은 설명용 발췌이며 실제 파일에는 모든 항목을 넣어 배점 합계를 100으로 맞춘다. 각 항목의 acceptance에는 그 기준을 적용할 문서 종류만 적는다. 문서별 총점은 해당 항목들의 배점 합계를 분모로 정규화한다.

```json
{
  "schema_version": 1,
  "criteria_id": "application-jd-v1",
  "jd": {
    "company": "지원 회사",
    "role": "지원 직무",
    "source": "제공된 공고 파일 또는 URL",
    "snapshot_sha256": "JD 원문 파일의 실제 SHA-256"
  },
  "documents": [
    {"id": "resume-ko", "kind": "resume", "language": "ko"},
    {"id": "resume-en", "kind": "resume", "language": "en"},
    {"id": "portfolio-ko", "kind": "portfolio", "language": "ko"}
  ],
  "formats": ["html", "pdf"],
  "threshold": 80,
  "category_floors": {"must_have": 75, "responsibilities": 75},
  "criteria": [
    {
      "id": "M1",
      "category": "must_have",
      "weight": 35,
      "source_type": "explicit",
      "jd_ref": "공고 필수 역량 항목·문단 위치",
      "requirement": "C++ 기반 로봇 SW 구현 경험",
      "critical": false,
      "min_level": 3,
      "acceptance": {
        "resume": "본인 구현 기능·C++ 사용 범위·확인된 산출물 설명",
        "portfolio": "입출력 구조·개인 수정 범위·시험 조건과 결과 설명"
      }
    }
  ]
}
```

대상 문서 ID는 리뷰 전후에 유지한다. 한·영 이력서를 새로 만들면 두 언어 모두 기준표에 포함한다. 포트폴리오는 사용자가 요청한 언어를 포함하며, 존재하는 한·영 버전 중 약한 버전을 제외하지 않는다. 사용자 요청으로 범위가 바뀌면 기준 버전을 올리고 이전 점수와 직접 비교할 수 없음을 기록한다.

`criteria.md`에는 같은 항목을 `ID / JD 위치·요건 / 명시·추론 / 배점 / 이력서 인수조건 / 포트폴리오 인수조건 / 사용할 근거 / 부족 자료`로 보여준다. 내부 QA 표는 지원 문서 본문과 분리한다.

## 초안 작성·수정 스킬과 연결

`html-a4-resume`, `html-pdf-portfolio`, `student-project-portfolio`에서 이 문서를 읽고 같은 기준을 사용한다. 공유 지원 건에 기준이 있으면 다시 만들지 않는다. 리뷰에서 수정 요청을 받은 제작 스킬은 전달된 기준 ID·수정 항목만 반영한 뒤 리뷰 호출자에게 결과를 돌려준다. 그 안에서 다시 리뷰 스킬을 실행하지 않는다.

기준이 가리키는 경험이 정본에 없으면 `필요 근거 없음`으로 남긴다. 핵심어 삽입, 숙련도 상향, 미측정 성과 생성, 비공개 고객명 노출로 조건을 채우지 않는다.
