# HTML PDF Portfolio

실제 업무·프로젝트·연구 자료를 근거로 수정 가능한 HTML과 PDF 포트폴리오를 만든다. 첫 취업·이직·경력 전환 모두 지원하며 특정 개인의 이력·회사·경로에 의존하지 않는다. 기획·디자인·마케팅·영업·운영·개발 등 직무에 맞는 근거를 사용한다.

## 자료와 질문

먼저 경력 기록·기획서·분석·디자인·운영 결과·연구·코드·README·기존 포트폴리오·이미지 등 제공 자료를 읽어 경험 목록과 근거를 정리한다. 희망 직무, 제출 조건, 본인 역할, 결과, 누락 자료를 확인한다. 코드·GitHub·실험이 없는 직무에 이를 강제하지 않는다. 자료에서 답을 찾을 수 없는 중요한 질문만 최대 3개로 묶어 묻는다. 사용자 답이 필요한 주장·저자명·역할은 확정하지 않는다. 답을 기다리는 동안 근거 목록과 문서 구조를 만든다.

모든 프로젝트는 목록에 남기되, PDF는 대표 사례를 선별해 설명한다. 목표와 실측, 시뮬레이션과 실기, 팀 성과와 본인 기여를 구분한다. 수치가 없으면 미측정으로 표시하고 가장 작은 추가 측정을 제안한다. 근거가 없는 그림은 캡처 요청으로 남긴다.

## 작성 전: JD 기준과 인수조건

JD가 있으면 사례·슬라이드 작성 전에 [공유 JD 기준](../jd-application-review/references/jd-criteria.md)을 읽고 필수요건·주요업무·우대사항을 실제 프로젝트 근거와 연결한다. 기준·배점·인수조건을 개인 QA 폴더에 먼저 기록하고 각 기준을 입증할 사례와 시각 자료를 고른다. 같은 지원 건의 이력서 기준이 있으면 재사용한다. 사용자가 요청한 모든 언어 버전을 포함하고 자료가 없는 경험은 없는 상태로 남긴다. JD가 없으면 목표 직무 기반 임시 구성 계획을 사용하며 JD 점수를 만들지 않는다.

리뷰에서 기준 ID·수정 항목을 받았다면 기준을 바꾸지 않고 기존 v1을 보존해 v2를 작성한다. 관련 이력서와 모든 언어에 기간·역할·성과를 일치시킨다.

## 구성

[chapter-structure.md](references/chapter-structure.md)를 읽는다. 기본은 **표지 → 성과 Summary → 일하는 방식(선택) → 회사·프로젝트별 간지와 핵심 성과 상세 → 수상·학력·역량 → 채용 가치 마무리**다. 각 회사·경험에서 핵심 성과 3~4개를 선별하되 실제 근거가 적으면 줄인다. 간지에 회사·역할·기간·업무 영역을 명확히 표시하고, 상세 페이지는 성과 하나와 실제 근거를 중심으로 구성한다.

제출 조건과 실제 자료량을 우선한다. 기본 HTML은 3개 챕터·각 3개 성과의 18쪽 예시이며 없는 경험을 채우지 않는다. 회사 경력이 없는 학생은 프로젝트·연구·캡스톤 단위로 묶는다. 짧은 제출이나 단일 프로젝트에는 압축 구성을 사용하고, 여러 회사의 충분한 근거를 무조건 8~10쪽으로 줄이지 않는다.

페이지마다 핵심 주장, 시각 근거, 출처를 정한다. **제목·Summary의 주요 문구는 검증된 성과·변화를 먼저 보여주는 명사형**으로 쓴다. 우선순위는 확인된 결과·지표 → 완료·적용한 산출물 → 직접 수행한 행동이며 도구명·활동 나열로 끝내지 않는다. 결론을 낼 수 없으면 미측정·진행 상태를 유지한 정확한 목표·산출물·검증 계획으로 제한한다. 제목을 강하게 만들기 위해 숫자·인과·개인 소유권을 부풀리지 않는다. 내부 기술명은 처음에 설명한다.

[project-onepager.md](references/project-onepager.md)를 읽고 회사 → 프로젝트 계층 아래에서 각 프로젝트의 대표 설명을 한 페이지로 정리한다. **한국어 제목은 결론형 명사구**, 본문은 문제·내 역할 / 해결·판단 / 성과·조건의 세 블록으로 작성한다. 이미지는 비율·해상도·증거 가독성을 보고 왼쪽·오른쪽·가운데 전체 너비 중 선택한다. 좌측 배치를 강제하거나 위치를 바꾸기 위해 원본을 반전·왜곡하지 않는다. 한 페이지에 맞출 때는 문구를 먼저 편집하고 중요한 증거를 작은 글씨나 무리한 크롭으로 숨기지 않는다.

## 구현과 출력

[design-review.md](references/design-review.md)를 읽는다. 공용 스킬에서는 테마색·Summary 벤토 팔레트를 사용자에게 맞춘다. 기존 자료·이미지·가이드에 선택이 없으면 한 번 묻는다: **“원하시는 테마색과 Summary 벤토 카드 색상이 있으신가요? 색상 코드·참고 이미지·스타일 가이드를 주시면 맞춰 적용하겠습니다. 없으면 기본 팔레트로 진행할 수 있습니다.”** 이미 선호가 확인됐으면 다시 묻지 않는다. 답을 기다리는 동안 JD 기준·경험 선별·내용 초안은 계속하고 색상을 최종 확정했다고 표시하지 않는다. 사용자가 기본 사용을 선택하면 예시 팔레트를 적용한다.

핵심 결론·실제 근거·여백 중심으로 디자인을 점검한다. `design-taste-frontend`가 있으면 문서에 맞는 정보 위계·타이포그래피·색상·리디자인 원칙만 적용한다. 없어도 연결된 지침으로 작업할 수 있다. 기본은 밝고 간결한 배경이며 사용자 테마가 있으면 그 방향을 우선한다. 벤토는 필요한 정보를 묶을 때만 사용한다. 장식용 배경·카드·생성 이미지가 근거를 대체해서는 안 된다.

[layout-and-export.md](references/layout-and-export.md)를 읽는다. [portfolio.html](assets/portfolio.html)은 편집용 시작 템플릿이며 실제 지원자의 실적이 아니다. `python3 tools/prepare_documents.py output/application/v1 --kind portfolio`로 복사하면 번들 폰트·라이선스와 상대 경로도 준비된다. 내용과 자산을 실제 자료로 교체한다.

- 한 페이지를 1600×900 고정 좌표로 구성한다. 브라우저에서는 페이지 전체를 비율로 축소하며 내부 내용을 화면 폭에 따라 재배치하지 않는다.
- [번들 Pretendard](../../assets/fonts/README.md)를 상대 경로로 로드한다. 설치·CDN 없이 사용하며 `document.fonts.ready`와 face loaded 상태를 확인한 후 출력한다. 번들 자산이 없는 환경만 대체 폰트와 실제 결과를 보고한다.
- 이미지는 `object-fit: contain`, 링크는 실제 `a href`로 넣는다. 외부 이미지 핫링크보다 출처가 기록된 로컬 자산을 사용한다.
- Chromium 인쇄로 같은 HTML을 PDF로 내보낸다. 텍스트·링크를 보존하고 스크린샷을 PDF로 합치지 않는다.

출력 후 페이지 수·16:9 비율·링크·한글 글리프를 확인한다. 모든 페이지를 렌더링해 디자인 인수조건, 겹침·잘림·여백·글꼴·근거 가독성을 점검한다. 내용이 넘치면 우선 문구와 중복을 줄이고 핵심 근거 크기를 유지한다. 디자인 첨삭은 페이지·요소별 문제와 정보 전달 영향, 실제 수정과 재확인 결과를 기록한다.

## 전달

HTML·PDF·사용 자산·근거 및 미확정 목록을 제공한다. 코드·README·포트폴리오의 기간·역할·결과가 일치하는지 확인한다. 생성·실행·시각 검증 중 실제 수행한 범위를 정확히 보고한다. 원본 자료를 공개 저장소로 자동 업로드하지 않는다.

JD가 있는 새 작성의 1차 출력 후 [JD 리뷰·수정 스킬](../jd-application-review/SKILL.md)로 같은 기준을 채점하고 수정·재출력·재검수한다. 사용자 지정 범위가 우선한다. **리뷰 스킬의 수정 단계에서 호출됐으면 재귀적으로 리뷰를 호출하지 않고** 갱신한 모든 언어의 HTML·PDF와 검사 결과를 반환한다.
