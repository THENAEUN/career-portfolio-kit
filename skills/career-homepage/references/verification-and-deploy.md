# 검증과 Vercel 배포

## 완료 기준

[환경·브라우저 지침](environment-and-browser.md)의 Playwright 설정·검증 흐름을 적용한다. 연결된 브라우저 도구를 우선 활용하고 필요할 때 프로젝트 내부 테스트 도구를 준비한다.

프로젝트의 실제 명령을 실행한다. 새 앱에는 typecheck와 lint 명령을 정의하고 빌드와 별개로 확인한다. 설치한 Next.js 버전에서 빌드가 lint를 자동 실행한다고 가정하지 않는다.

```bash
npx tsc --noEmit
npx eslint .
npm run build
npm run start
```

기존 프로젝트에 전용 스크립트가 있으면 그것을 쓴다. production 서버로 아래 동작을 검증한다. 자동화는 실제 버그 위험이 있는 파서·공개 필터·페이지 경계에 집중하고 단순 스타일 문구를 복제하는 테스트는 만들지 않는다.

| 대상 | 확인할 결과 |
|---|---|
| 홈·내비게이션 | 실제 소개·프로젝트 근거와 일치, 모바일 메뉴·블로그 탭·다운로드/연락처 링크 동작 |
| `.md` 첫 글 | 제목·작성일·본문·표·코드·중간 이미지가 같은 템플릿에서 표시, 한글/줄바꿈 확인 |
| 공개 필터 | draft true·미래 글은 목록/상세/JSON/관련 글/sitemap에 없음. 직접 주소도 404 |
| 재빌드 | 발행했던 글을 초안으로 바꾼 뒤 다시 빌드하면 오래된 JSON/HTML에도 남지 않음 |
| 데이터 오류 | 빠진/잘못된 필드, 불가능한 날짜, 중복/예약 slug, 위험 URL·경로, 누락 로컬 이미지 처리 |
| 페이지 경계 | 0·1·페이지 크기·페이지 크기+1·2페이지 이상, 안정 정렬, 중복·누락 없음 |
| 무한스크롤 | 로딩·마지막·실패·재시도, 중복 요청 방지, 빠른 스크롤, 더 보기 버튼, 뒤로가기 |
| JS 없는 탐색 | `/blog/page/2` 직접 진입과 다음/이전 `<a href>`를 따라 공개 글 전부 접근 |
| SEO | 초기 HTML에 본문·첫 목록 존재, 글별 title/description/canonical/OG, sitemap/robots 실제 주소 |
| 보안·공개 | 원본 경력 DB/근거표/초안/비밀이 public·클라이언트 데이터·Git 추적·출력 산출물에 없음 |

실제 브라우저에서 375px 안팎의 모바일·768px·데스크톱을 확인한다. 한국어 폰트, 전체 가로 넘침, 긴 제목, 이미지 비율·링크, 본문 너비, 키보드 포커스, 빈 상태를 점검한다. 사용 가능한 브라우저 도구로 홈·목록·본문 캡처를 개인 QA 위치에 남긴다. 테스트 글은 가상 자료로 임시 공간에서 사용하고 공개 배포에는 포함하지 않는다.

브라우저나 배포 권한이 없어 수행하지 못한 검사는 미검증으로 기록한다. 빌드 통과만으로 무한스크롤·모바일·배포까지 검증했다고 말하지 않는다.

## 배포 전 확인

1. 배포 요청/권한, 공개할 소개·프로젝트·연락처·PDF·글의 범위, 대상 Git 원격·브랜치·Vercel 계정/프로젝트를 확인한다. 이미 받은 답은 재질문하지 않는다.
2. [Vercel Hobby](https://vercel.com/docs/plans/hobby)의 현재 개인·비상업 용도 및 사용량 제한을 확인한다. 무료를 보장하거나 한도를 코드에 영구 고정하지 않는다. 회사/유료 사업 목적이면 무료 사용 가능하다고 단정하지 말고 적합한 플랜을 확인한다. 유료 업그레이드·도메인 구매는 수행하지 않는다.
3. 개인 사이트는 공용 키트와 분리된 사용자 소유 Git 저장소를 사용한다. 기존 원격을 무단 변경하지 않는다. `.env*`, `.vercel`, node_modules, .next, 내부 QA 자료를 Git에서 제외한다. 공개할 이력서 PDF에 숨은 개인정보·내부 링크도 확인한다.
4. 앱 프로젝트의 루트와 Build/Install 명령을 확인한다. 모노레포라면 Root Directory를 사이트 폴더로 지정하고 커리어 DB나 키트 전체를 공개 배포 루트로 선택하지 않는다.

## 권장: Git 연동

Vercel 대시보드에서 Add New → Project → 사이트 Git 저장소 Import → Framework Preset Next.js → Root Directory/설치·빌드 명령 확인 → Deploy 순서로 진행한다. 환경마다 UI 명칭은 다를 수 있다. [공식 Git 배포 문서](https://vercel.com/docs/git)를 확인한다.

사용자가 GitHub/Vercel 로그인을 직접 처리하고, 인증된 도구가 있으면 그 범위에서 작업한다. 자동 작업이 불가능하면 정확히 필요한 단계에서 사용자에게 넘기고 결과 URL을 확인한다. 계정 비밀번호·인증 토큰을 문서나 채팅에 적게 하지 않는다.

기존 Git 연결은 유지하고 요청된 변경을 반영한다. Hobby 배포가 차단되면 커밋 작성자와 Vercel 팀 소유자·저장소 소유권 조건도 공식 문서로 확인한다. 이를 우회하려고 작성자 신원을 바꾸지 않는다.

## 선택: CLI

CLI를 선택했고 프로젝트 인증이 준비됐으면 실행 시점의 [CLI 배포 문서](https://vercel.com/docs/cli/deploy)를 확인한다. 전역 설치 없이 프로젝트 루트에서 사용할 수 있다.

```bash
npx vercel login
npx vercel
```

첫 배포는 Preview로 확인한다. Production 공개가 요청/승인된 경우에만 다음을 수행한다.

```bash
npx vercel --prod
```

로그인·프로젝트 연결이 이미 완료됐으면 반복하지 않는다. 배포 권한이 없거나 로그인이 막히면 로컬 산출물과 검사 결과를 먼저 완성하고 남은 단계·사용자 조치만 명확히 남긴다. 로컬 완료와 배포 완료를 구분한다.

## 배포 후 인수

- 실제 반환된 URL에서 홈·블로그 목록·글·이미지·404·모바일을 확인한다. 로컬 파일만 확인한 상태를 공개 검증으로 표시하지 않는다.
- Production 도메인을 기준으로 canonical·OG·sitemap을 다시 확인한다. 필요한 경우 사이트 URL 설정을 갱신하고 재배포한다. Preview 도메인이 검색에 노출되지 않도록 설정을 확인한다.
- 공개 방문자의 접근 상태와 Production의 의도치 않은 보호/noindex를 확인한다. 의도한 비공개 보호는 유지한다.
- 사용자가 글 하나를 수정·추가하는 방법, 이미지 경로, `draft: false`, Git 반영과 자동 재배포 흐름을 프로젝트 문서에 남긴다. 도메인 변경·콘텐츠 삭제도 새 빌드가 필요한 점을 설명한다.

최종 전달 예시: 프로젝트 위치 / 로컬 실행 명령 / 글·이미지 위치 / 실제 확인 항목 / 미확정·미검증 / Git 업로드 상태 / Preview 또는 Production URL. Vercel 계정 연결이나 인증이 남았으면 배포 완료로 보고하지 않는다.
