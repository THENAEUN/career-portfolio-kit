# Career Homepage

사용자가 제공한 개인 커리어 DB·이력서·포트폴리오를 바탕으로 **반응형 개인 홈페이지와 Markdown 블로그를 실제 개발**한다. 기본은 Next.js App Router + React + TypeScript + Tailwind CSS, Vercel 배포다. 공용 키트에는 지침과 가상 템플릿만 유지하고 실제 사이트·개인 자료는 사용자가 지정한 별도 프로젝트에서 관리한다.

## 1. 자료 확인과 비개발자 질문

먼저 현재 프로젝트의 AGENTS.md, package.json, 잠금 파일, 기존 화면, 제공한 경력 자료와 접근 가능한 연결 소스를 확인한다. DB라는 이름만으로 새 데이터베이스를 만들지 않는다. 기존 개인 자료 저장소·Notion·폴더·문서에서 허용된 범위만 읽고 경력·기간·역할·성과·출처를 대조한다. 특정 개인의 계정·절대 경로·비공개 저장소를 전제하지 않는다.

이미 답이 있는 것은 다시 묻지 않고, 부족한 내용만 최대 3개 질문으로 묶는다. 기술 선택을 사용자에게 떠넘기지 않는다.

1. **스타일:** “밝고 간결한 편집형(추천), 이미지 중심, 차분한 다크 중 어떤 느낌이 좋으세요? 참고 사이트나 원하는 색이 있으면 함께 알려 주세요.”
2. **사이트 목적·자료:** “어떤 직무·활동을 보여주고 싶으세요? 기존 커리어 자료·이력서·포트폴리오 위치와 공개할 연락처·다운로드 문서를 알려 주세요.” 자료가 있으면 실제 누락 부분만 묻는다.
3. **첫 글:** “첫 글은 어떤 이야기를 쓰고 싶으세요? 자료에서 찾은 [실제 프로젝트 회고], [판단 과정], [문제 해결] 중 추천 주제나 원고·이미지를 주셔도 됩니다.” 실제 자료에서 뽑은 주제 2~3개를 제시한다.

선택을 기다리는 동안 근거 정리와 프로젝트 점검은 진행한다. 기본 사용을 선택하거나 스타일 결정 위임을 받으면 밝은 배경·Pretendard·절제된 포인트색·큰 제목과 충분한 여백을 적용한다. 선택 응답이 없으면 잠정 기본으로 로컬 초안을 진행하되 미확정 선택임을 알린다. 소재·주장이 필요한 본문과 외부 공개는 답변/권한 없이 확정하지 않는다.

키트의 HTML/PDF 포트폴리오는 내용·자산의 참고 자료다. 고정 16:9 슬라이드를 웹에 그대로 축소해 붙이지 않고 모바일과 웹 읽기 흐름에 맞게 다시 구성한다. `design-taste-frontend`가 사용 가능한 환경이면 웹 디자인에 적용하되 없어도 이 지침만으로 완수한다.

## 2. 내용과 공개 범위

개인 작업 공간에 출처 대응표를 만든다: `웹 섹션/주장 → 원본 위치 → 확인된 사실 → 공개 가능 여부`. 커리어 정본과 기존 제출 문서가 다르면 임의 선택하지 말고 충돌을 표시해 확인한다. 자료에 없는 경력·숫자·고객명·추천사·인과를 만들지 않는다. 팀 결과와 본인 기여, 목표와 실측, 개발 완료와 배포 상태를 구분한다.

비공개 DB 연결은 **작성 시 자료 읽기용**을 기본으로 한다. 방문자가 매번 커리어 DB를 조회하게 하거나 원본 DB 전체를 프론트에 번들하지 않는다. 공개하기로 한 내용만 `content/profile`과 프로젝트 데이터로 옮긴다. 비공개 원본·근거표·내부 경로·토큰은 public/·클라이언트 props·Git·배포 산출물에 포함하지 않는다. 사용자가 제공한 공개 이메일·프로필 링크·PDF만 사이트에 표시한다.

홈 구성은 소개/대표 프로젝트/경력 요약/공개 연락처를 기본으로 실제 자료량에 맞춘다. 내비게이션에 **블로그**를 독립 메뉴로 추가한다. 프로젝트 상세가 필요하면 `/projects/[slug]`, 소개는 섹션 또는 `/about`으로 구성한다. 없는 항목은 숨긴다. 자료가 불충분하면 확인 가능한 내용으로 로컬 초안을 만들고 빠진 사실을 명시한다.

## 3. 설치부터 프론트엔드 개발

[환경·브라우저 지침](references/environment-and-browser.md)으로 Mac/Windows/WSL·셸·Node/npm/Git·브라우저 도구를 감지하고, [구현 지침](references/implementation.md)을 읽어 기존 프로젝트 재사용 여부와 적용 버전을 정한다. 순서는 **환경 확인 → 프로젝트 생성/의존성 설치 → 홈페이지 → 블로그 목록/본문 → SEO → 검증 → 배포**다. 매 단계 명령·결과·막힌 부분을 짧게 설명하고 실행 가능한 환경에서는 직접 수행한다. 명령만 나열하고 개발이 완료됐다고 말하지 않는다.

사용자가 웹 개발을 요청하면 프로젝트 내부의 필요한 패키지 설치를 진행한다. 이미 설치된 의존성과 잠금 파일을 보존한다. Node 자체가 없으면 OS별 공식 LTS 설치 방법을 안내하고 시스템 설치에 필요한 승인을 처리한다. 전역 패키지 설치·dotfile 수정·유료 서비스 추가를 기본값으로 삼지 않는다. 프레임워크의 현재 공식 요구사항과 실제 설치 버전을 확인하고 잠금 파일로 재현성을 남긴다.

**Next.js를 기본으로 추천하는 이유:** React 컴포넌트와 Tailwind 디자인을 사용하면서 글별 HTML 사전 생성, 메타데이터, sitemap, 공유 미리보기를 함께 구성하기 쉽다. SEO에 Next.js가 반드시 필요한 것은 아니며 검색 순위·색인을 보장하지 않는다. 기존 사이트가 다른 프레임워크라면 목적 달성을 위해 전면 재작성할 필요가 있는지 먼저 판단한다.

## 4. Markdown 블로그와 첫 글

[블로그 규약](references/blog.md)을 읽는다. 글 원본은 `content/blog/<slug>.md`, 이미지는 `public/images/blog/<slug>/`에 둔다. 목록 `/blog`, 다음 목록 `/blog/page/2`, 본문 `/blog/<slug>`를 공통 템플릿으로 렌더링한다. 별도 DB·CMS·로그인·관리자 페이지를 기본 도입하지 않는다.

[첫 글 템플릿](assets/first-post.md)을 선택한 주제와 검증된 사실로 채워 **실제 `.md` 파일 1개**를 만든다. 제목·작성일·요약·본문을 작성하고 본문 중간 이미지도 지원한다. 이미지가 없으면 깨진 경로를 넣지 않고 개인 작성 메모에 캡처 요청을 남긴다. 원고가 없으면 초안으로 작성하고 `draft: true`를 유지한다. 사용자가 글 내용·공개를 승인한 범위에서만 발행한다. 가상 템플릿을 본인의 실제 경험으로 발행하지 않는다.

읽기 편한 제목/소제목/문단/이미지/캡션/표/인용/코드 스타일을 제공한다. 토스 테크는 콘텐츠 위계·여백·읽기 흐름의 참고이며 로고·브랜드 자산·글을 복제하지 않는다. 무한스크롤은 페이지 단위로 추가 로드하고 일반 링크·더 보기 대안을 유지한다. 초기 HTML과 독립 페이지로 전체 공개 글을 탐색할 수 있어야 한다.

MDX는 인터랙티브 컴포넌트가 실제 필요한 경우만 추가한다. 외부 입력·방문자 업로드를 MDX 코드로 실행하지 않는다.

## 5. 검증과 Vercel 배포

[검증·배포 지침](references/verification-and-deploy.md)을 읽는다. 사용 가능한 Playwright/브라우저 도구로 실제 로컬 화면을 보며 개발·수정·재확인하고, 도구가 없으면 환경 지침에 따라 프로젝트 내부 Playwright Test를 준비한다. 설치 안내만으로 멈추지 말고 실행 가능한 검증까지 수행한다. 홈페이지·실제 글 1개·빈 목록·404·초안 숨김·페이지 경계·이미지·모바일·접근성·SEO를 확인한다. 대량 글이 없어도 가상 테스트 글은 임시 공간에서 페이지 크기보다 많이 만들어 검증하고 공개 콘텐츠에는 남기지 않는다.

Vercel은 무료 개인 프로젝트를 기본으로 안내하되 실행 시점의 Hobby 용도·사용량 제한을 공식 문서에서 확인한다. 유료 업그레이드·도메인 구매는 별도 선택이다. 배포 요청이 이미 있으면 범위 내에서 진행하고 반복 확인을 요구하지 않는다. 배포 권한이 없으면 먼저 로컬 완성본·검증 결과와 공개할 내용을 준비한 뒤 구체적 배포 대상의 승인만 요청한다. 키트에 스킬을 추가하라는 요청만으로 개인 홈페이지 공개까지 허가된 것은 아니다.

완료 시 프로젝트 위치, 실행 방법, 글/이미지 추가 방법, 검증 결과, 미확정 내용, 로컬/업로드/Preview/Production 상태와 실제 URL을 전달한다. 계정 인증이 필요하면 사용자가 로그인하도록 안내하고 비밀번호·토큰을 채팅이나 저장소에 요구하지 않는다. 실제 공개 URL을 확인하기 전에는 배포 완료라고 말하지 않는다.
